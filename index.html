Part 1 · From LLM to chatbot

Text completion: the only native skill

Generation is a loop around the model: predict a distribution, sample one token, append it, run again.

Context: every token so far

Distribution

over the whole vocabulary

Sampler

Stop: end token or length limit

read all of it

One trip around the loop per generated token. A 500-token answer is 500 forward passes.

Sampling

Temperature and top-p reshape the distribution before one token is drawn. At temperature 0 the most likely token always wins.

Stopping

The model was trained to emit a special end token when a document is finished. The sampler stops there.

The model has no other operation. Chat, tools and agents are all this loop, run on a carefully built context.

Part 1 · From LLM to chatbot

How the model learns the assistant role

The format alone is not enough. Further training makes “continue this transcript” mean “answer helpfully”.

1

Pretraining

Data

A very large corpus of general text and code.

Objective

Predict the next token.

Result: a base model that continues any document.

2

Instruction tuning

Data

Curated conversations written in the chat format, including tool calls.

Objective

The same next-token loss, applied to the assistant turns.

Result: follows instructions, stays in role, ends its turn.

3

Preference tuning

Data

Ratings and comparisons of candidate answers (RLHF and related methods).

Objective

Make highly rated answers more likely.

Result: more helpful, honest and careful answers.

Later skills in this deck, such as emitting a tool call or reasoning before answering, are learned the same way: as patterns in training conversations.

The model decides

Whether a tool is needed, which one, and with what arguments. Its entire contribution is a few lines of generated text.

It parses the request, checks it, runs the real function and enforces permissions. The model never touches anything directly.

Part 2 · Tool use

A tool definition

A tool is described to the model with a name, a plain-language description and a JSON Schema for its arguments.

Sent with every request, next to the messages

{
  "name": "get_weather",
  "description": "Get the current weather for a city.
    Use when the user asks about weather
    or what to wear outside.",
  "input_schema": {
    "type": "object",
    "properties": {
      "city": {"type": "string",
               "description": "City name"}
    },
    "required": ["city"]
  }
}

name

The identifier the model writes when it wants this tool.

description

The prompt for this tool: the model reads it to decide when to call. Vague text causes missed or wrong calls.

input_schema

The contract for arguments. The harness validates against it; many APIs can also constrain decoding to it.

Definitions are rendered into the prompt. To the model they are more context tokens, which it learned to answer with tool calls.

Part 3 · RAG

Embeddings: meaning as geometry

An embedding model maps a piece of text to a vector. Texts with similar meaning land close together.

shipping chunks

account login chunks

refund policy chunks

query: “How do I get my money back?”

A 2-D sketch. Real embeddings have hundreds to thousands of dimensions.

Text in, vector out

embed("Refunds within 30 days")

→ [0.12, -0.48, 0.33, …]

Closeness is a number

cos(q, d) = q·d / (‖q‖ ‖d‖)

Search returns the k chunks with the highest score. Approximate nearest-neighbour indexes such as HNSW do this over millions of vectors in milliseconds.

The query shares no word with “refund”, yet lands beside it: retrieval by meaning, not by keyword.

 "vector": [0.12, -0.48, 0.33, …],
 "meta": {"title": "Refund policy", "section": "2.1"}}

Too small

The match is precise, but the passage lacks the surrounding sentences needed to answer.

Too large

One vector must stand for several topics, so matches blur and the prompt fills up.

Common practice

A few hundred tokens, 10–20% overlap, split on headings and paragraphs. Keep metadata for filters and citations.

Part 3 · RAG

Retrieve wide, then rerank

Vector search is fast but coarse. Production systems run two retrievers, then let a slower, sharper model reorder the shortlist.

Index

millions of chunks

Dense search

nearest vectors:
matches meaning

Keyword search (BM25)

matches exact terms:
names, codes, ids

Fuse

about 100 candidates

Reranker

scores each candidate against the question

Top 5

go into the prompt

Hybrid search

Embeddings blur exact strings such as an error code or a product name. Keyword search catches them. Rank fusion merges the two lists.

Embedding search

Question and chunk are encoded separately, so chunk vectors are computed once in advance. Cheap enough for the whole corpus.

Reranker

A cross-encoder reads question and chunk together and outputs one relevance score. More accurate, but only affordable on a shortlist.

Grounding instructions. “Use only the documents” and “say so if it is missing” reduce made-up answers.

Ids. Every chunk carries an id, so each claim can be checked against its source.

Less is more. A few relevant chunks beat many loosely related ones.

Part 4 · The agent loop

The agent loop

Every agent, whatever the product, runs some version of this cycle.

Context

Model

Harness

Tool

runs for real

Final answer

1 · send all of it

2 · text, tool calls, or both

3 · yes: execute

4 · append the result

no: done

One trip around = one model call.
A task may take a few trips or hundreds.

What the model sees

On every trip it rereads the whole context: instructions, tool definitions and everything that has happened so far.

What ends the loop

A reply with no tool call. The harness also stops on a turn limit, a budget, or an interrupt from the user.

Where the intelligence is

The loop is trivial code. Choosing the next action, and judging when the task is finished, is entirely the model.

Part 4 · The agent loop

The agent loop in 15 lines

Python-style pseudocode. Real harnesses add streaming, permissions and error handling around this core.

def run_agent(task, tools, max_turns=50):
    messages = [{"role": "user", "content": task}]   # 1

    for turn in range(max_turns):
        reply = llm(SYSTEM_PROMPT, tools, messages)  # 2
        messages.append(reply)

        if reply.stop_reason != "tool_use":          # 3
            return reply.text

        for call in reply.tool_calls:                # 4
            result = execute(call.name, call.input)
            messages.append(tool_result(call.id, result))

    return "stopped: turn limit reached"

1

The message list is the agent’s entire state. Nothing else carries over from one turn to the next.

2

One model call per turn, always with the system prompt, the tool definitions and the full history.

3

The exit. A reply that asks for no tool means the model considers the task finished.

4

Results go back in as messages, so the next turn can read them. Errors are returned the same way, and the model reacts to them.

The harness is this loop plus the system prompt, the tools and the safety checks around execute().

Part 4 · The agent loop

Reasoning between actions

Models act better when they write their reasoning down first, then check it against real observations.

One task, as a thought · action · observation trace

Task

Chain of thought

Asking for step-by-step reasoning before the answer improves multi-step accuracy. The reasoning is just more generated tokens that later tokens attend to.

ReAct

Interleave reasoning with actions and observations, so each thought is grounded in real feedback instead of a guess.

Extended thinking

Current models are trained to reason in a dedicated thinking block before each reply or tool call. The mechanism is built in rather than prompted.

Why code suits agents

Software has four properties that make the loop work unusually well. Few other domains have all of them.

All text

Source, configs, logs, errors and diffs are the model’s native medium.

2

Automatic verdicts

Compilers, tests and linters say exactly what is wrong, within seconds.

3

Tools exist

One shell tool reaches git, package managers, test runners and every CLI.

4

Easy to undo

Version control and sandboxes make a wrong step cheap to reverse.

The list is short. Tool names vary by product; these six capabilities are nearly universal.

How an edit travels

{"name": "Edit", "input": {
  "file_path": "src/auth.py",
  "old_string":
    "if password == None:",
  "new_string":
    "if not password:"}}

The harness applies it, and refuses if the old string is not found exactly once. The model therefore has to read a file before changing it.

Why not rewrite the file? A small replacement costs few tokens, cannot silently drop unrelated lines, and gives the user a reviewable diff.

Part 6 · Context and memory

The context window as a budget

Everything the model knows about the task has to fit in one window, and every turn adds to it.

Turn 1

11% used

Turn 20

tool results

55% used

Turn 60

tool results: files read, command output, search hits

96% used

System prompt

Tool definitions

Conversation

Tool results

Free

Proportions are illustrative.

Tool results dominate

One file read or test log can be thousands of tokens. The model’s own words are a small share.

Fixed overhead, every turn

The system prompt and tool definitions are resent on each call. Prompt caching makes rereading them cheap.

Fuller is not better

As a context grows very long, models attend less reliably to details in it. Quality can drop well before the hard limit.

Treat context as scarce: aim for the smallest set of high-signal tokens that lets the model do the next step.

Part 6 · Context and memory

Skills: instructions loaded on demand

A skill is a folder of instructions and scripts for one kind of task. Only its one-line description sits in context until needed.

A skill on disk

pdf-forms/
  SKILL.md
  reference/fields.md
  scripts/fill_form.py

SKILL.md

---
name: pdf-forms
description: Fill in PDF forms. Use when
  the user asks to complete a PDF.
---
1. Read reference/fields.md
2. Run scripts/fill_form.py …

Three levels, loaded progressively

1 · Name and description

Always in context. A line or two per skill.

2 · The body of SKILL.md

Read when the model judges that the task matches the description. About a page.

3 · Bundled files and scripts

Opened or executed only when the instructions point to them. As large as needed, at no cost until used.

MCP gives an agent new tools. A skill gives it know-how for the tools it already has, without spending context until the moment it is relevant.

Part 7 · Multi-agent systems

Why split work across agents

A sub-agent is a second agent loop with its own context window. Splitting has gains and costs.

One agent · everything in one window

Three research threads, all their search results, one crowded context.

Lead + three sub-agents · four windows

Lead

A

B

C

What you gain

Context isolation. Each sub-agent explores in a clean window and hands back only a summary, so the lead stays uncluttered.

Parallelism. Independent subtasks run at the same time.

Specialisation. Each role can have its own system prompt, tools, and even a different model.

What it costs

Tokens. Several loops run at once. Anthropic reported its multi-agent research system using about 15× the tokens of a chat (2025).

Lost detail at handoffs. A sub-agent knows only its brief; the lead sees only the summary.

Coordination failures. Duplicated work, conflicting edits, harder debugging.

Start with one agent. Split when the task is broad, parallel, and too large for a single window.

The brief is everything. The worker has none of the lead’s history. The goal, the constraints and the expected output format all have to be in the prompt.

Only the final message returns. Whatever the worker read along the way stays in its own window and is then discarded.

Part 8 · Evaluation and safety

Evaluating an agent

A chatbot is graded on its text. An agent is graded on the state of the world after it finishes.

Three kinds of grader

Code checks. Do the hidden tests pass? Does the file exist? Objective and cheap; the default whenever possible.

A model as judge. A second LLM scores open-ended output against a rubric. It must be calibrated against human labels.

Human review. The reference standard, and slow. Mostly used to validate the other two.

Why real agents beat the curve

The curve assumes a wrong step is never noticed. An agent that runs tests, reads error messages and reviews its own output turns silent failures into observations, and recovers.

Part 8 · Evaluation and safety

Layers of defence

No single measure is enough. Safe agent systems stack several, so that one failure does not become an incident.

1 · Sandbox. An isolated file system and a restricted network. Whatever happens stays inside.

2 · Least privilege. Only the tools and credentials this task needs, scoped as narrowly as possible.

3 · Permission prompts. A person approves risky or irreversible actions before they run.

4 · The model itself. Trained and instructed to treat tool results as data, not as commands.

The action: a tool call

Match the check to the possible damage

ActionExampleTypical policy
ReadOpen a file, search the webAllow
Reversible changeEdit a file under version controlAllow, and show the diff
ExecuteRun a shell commandAllow-list, or ask
Irreversible or externalSend email, deploy, delete, payAlways ask a person

Keep a trace. A log of every tool call, with its arguments and result, makes failures debuggable and actions auditable.

Autonomy is granted per kind of action: more potential harm, more checks in front.
